# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TradeOS is a virtual (paper) trading platform for Indian equities (NSE/BSE, INR). New users get a wallet with ₹1,00,000 of virtual money and can buy/sell stocks, track holdings, portfolio P&L, orders, transactions and a watchlist. The repo has two independent npm projects: `server/` (Express 5 + Mongoose, ESM JavaScript) and `client/` (React 19 + Vite, plain JSX, no TypeScript). `docs/RoadMap.txt` lists the development phases; backend (Phase 4) is done and frontend (Phase 5) is in progress. Per-feature plans and build checklists live in `docs/plans/` (e.g. `portfolio-page.md`).

## Commands

Run each from its own directory (`server/` or `client/`).

Server:
- `npm run dev`: start with nodemon (port from `PORT`, default 8080)
- `npm start`: start without reload
- `npm run test:run`: run all tests once (`npm test` runs vitest in watch mode)
- `npx vitest run tests/orders.integrated.test.js`: run a single test file
- `npx vitest run -t "should buy a stock successfully"`: run a single test by name
- `node src/modules/stocks/stock.seed.js`: wipe and reseed the `stocks` collection with dummy data
- `node scripts/backfill-market-history.js`: DRY RUN of the one-time price-history backfill (prints the connection and a plan, writes nothing). `--apply --confirm-db=<database name>` writes. It only inserts, skips stocks that already have candles, never touches prices or user data, and refuses to run in production. `NODE_ENV=test` targets the test database.

Client:
- `npm run dev`: Vite dev server on http://localhost:5173
- `npm run build`, `npm run lint` (ESLint), `npm run preview`
- There are no frontend tests. To check pages by eye, `npm run screenshots <label>` saves desktop and phone screenshots of every page and open state to `client/screenshots/<label>/` (git-ignored) and reports page errors, failed requests and pages that scroll sideways. It uses the installed Edge, only the TEST database, and needs two servers running first: `cd server && NODE_ENV=test PORT=8081 CORS_ORIGIN=http://localhost:5174 node src/server.js` and `cd client && VITE_API_BASE_URL=http://localhost:8081 npx vite --port 5174 --strictPort`, then `BASE_URL=http://localhost:5174 API_URL=http://localhost:8081 npm run screenshots before`. Do not stop the developer's own dev server on 5173.

## Environment

- `server/src/config/env.js` loads `.env`, or `.env.test` when `NODE_ENV=test` (vitest sets this automatically). It throws at startup if `MONGODB_URI`, `JWT_ACCESS_SECRET` or `FRONTEND_URL` is missing. Import config from this module rather than reading `process.env` directly.
- Client needs `VITE_API_BASE_URL` (backend origin) in `client/.env`.
- The backend CORS origin comes from the optional `CORS_ORIGIN` setting and defaults to `http://localhost:5173` (it does not use `FRONTEND_URL`: in `server/.env` that value is written with quotes and a `;` and parses as `'http://localhost:5173';`).
- `MARKET_ALWAYS_OPEN=true` (optional, development only): the market counts as always open, so prices move and orders work at night. `config/env.js` refuses to start with it unless `NODE_ENV` is explicitly `development` or `test`. vitest sets it to true for every test file (`vitest.config.js`); the closed-market tests turn it off themselves.
- MongoDB must support multi-document transactions (replica set / Atlas). Order placement and registration depend on it.

## Backend architecture (`server/src`)

Modular monolith architecture is being followed
- `app.js` builds the Express app (middleware, routes under `/api/<module>`, then 404 handler, then the central error handler). `server.js` connects to MongoDB and listens. Tests import `app.js` directly with supertest.
- Feature modules live in `modules/<name>/` with a consistent layering: `*.routes.js` → `*.controller.js` → `*.service.js` → `*.model.js`, plus optional `*.validation.js` (Joi schemas). Controllers stay thin (read `req.user.userId` / body / query, call the service, send the response); business logic lives in services. Services export a default object of functions.
- Route chain pattern: `protect` (JWT auth) → `validate(schema, "body" | "query" | "params")` → controller wrapped with `asyncWrap`.
- Errors: throw `new AppError(message, statusCode, ERROR_CODES.X)` (`utils/AppError.js`, `utils/errorCodes.js`). `middleware/error.middleware.js` returns `{ success: false, message, errorCode }` for these; anything else becomes a generic 500. The frontend relies on `errorCode`, so add new codes to `errorCodes.js`.
- Success responses use `{ success: true, message, data }`. Paginated lists return `data: { items, pagination: { page, limit, totalItems, totalPages, hasNextPage, hasPreviousPage } }`; query params are validated with `utils/pagination.validation.js`.
- Shared Joi rules live in `utils/validation.js` (`objectIdSchema`, `nameSchema`). The `validate()` middleware strips unknown fields, so a route only ever sees the fields its schema lists.
- Gotcha: many server files (the users, auth and utils modules, for example) use Windows (CRLF) line endings, so a multi-line text replacement can fail to match. Check with `grep -c $'\r' file` and preserve the endings when rewriting.
- **Trading flow** (`orders/order.service.js`): buy/sell run inside a Mongoose session transaction that atomically creates the Order (status `EXECUTED`), updates the Wallet balance, upserts or deletes the Holding (weighted average buy price on buy), and writes a Transaction record. Orders execute at `Stock.currentPrice` from the database, **not** the live FYERS price. Portfolio P&L (`portfolio.service.js`) is likewise computed from `Stock.currentPrice` on the fly. `Stock.currentPrice` is moved by the simulated price job (below). All money maths goes through `utils/money.js` (whole paise, see below). Buy and sell answer 403 `MARKET_CLOSED` while the market is closed, and each order runs through `utils/retryTransaction.js`, which repeats it (up to 8 attempts, exponential backoff with jitter, re-reading the latest price) when MongoDB aborts it with a `TransientTransactionError` (for example two orders from one user at the same moment); after that it answers 409 `ORDER_CONFLICT`.
- **Auth** (`modules/auth`): argon2 password hashes; registration creates the User and Wallet in one transaction. 15-minute JWT access token (payload `{ userId, role }`) sent as `Authorization: Bearer`. Refresh token is a random string stored hashed in `RefreshSession` with a `familyId`, delivered as an httpOnly `refreshToken` cookie and rotated on every `/api/auth/refresh`. Rotation is atomic (the old token is claimed with one `findOneAndUpdate`, the new session is created first). Reusing an old refresh token revokes the whole family (`REFRESH_TOKEN_REUSE`), EXCEPT within a 10 second grace period after a normal rotation (`rotatedAt` on `RefreshSession`; covers two tabs and lost responses, and only while the login still has a live token, so a logout cannot be undone). `protect` answers an expired access token with 401 `ACCESS_TOKEN_EXPIRED` (bad signature: `ACCESS_TOKEN_INVALID`); the frontend renews on exactly those two codes. `POST /api/auth/register` and `/login` are limited to 10 requests per IP per 15 minutes (`authRateLimiter`, `AUTH_RATE_LIMIT`); `/refresh` has its own looser limiter (`refreshRateLimiter`, 100) because renewals are routine. All these IP limiters are skipped when `NODE_ENV=test` (the suite registers many users from one IP); `createIpRateLimiter({ limit, message, skip })` lets a test build an active one.
- **Change password** (`PATCH /api/auth/password`, protected): verifies the current password, saves the new hash and revokes the user's other refresh sessions in one transaction; the device whose refresh cookie accompanies the request keeps its login (no cookie means all sessions are revoked). Only failed attempts are rate-limited (`passwordChangeRateLimiter`, 5 per user per 15 min, in-memory). Signed-out devices keep a working access token until it expires (up to 15 min) but cannot renew it; an instant cut-off would need a `passwordChangedAt` check in `protect`.
- **Delete account** (`DELETE /api/users/me`, protected, body `{ password }`): re-checks the password (400 `INVALID_PASSWORD`; `accountDeletionRateLimiter`, 5 failed attempts per user per 15 min), then in one transaction deletes the user's transactions, orders, holdings, watchlist, wallet, login sessions and the user; the Cloudinary photo is deleted afterwards (best effort) and the login cookie is cleared. Stocks and the FYERS token are shared and stay. After deletion the old access token passes `protect` for up to 15 min: reads and updates answer 404 and orders fail, and `addToWatchlist` checks the user exists so it cannot leave orphaned entries. Any NEW endpoint that creates user-owned data must also check that the user (or their wallet) still exists.
- **Profile photos** (`modules/users`): `POST /api/users/me/avatar` (multipart field `avatar`, JPG/PNG/WebP, max 2 MB) and `DELETE /api/users/me/avatar`. `middleware/upload.middleware.js` reads the file in memory with `multer` and checks its real first bytes (`utils/imageType.js`); `utils/cloudinary.js` uploads it as a 256x256 square under the fixed id `tradeos/avatars/<userId>`, so a new upload replaces the old one. MongoDB stores only `avatar.url` and `avatar.publicId`. The three `CLOUDINARY_*` variables live in `server/.env` and are optional in `config/env.js`; without them the upload answers 503 `IMAGE_UPLOAD_UNAVAILABLE`. `uploadRateLimiter` allows 20 uploads per hour per IP.
- **Notifications** (`modules/notifications`, plan in `docs/plans/notifications.md`): four types (`ORDER_EXECUTED`, `WELCOME`, `LOW_BALANCE`, `PASSWORD_CHANGED`), deleted after 30 days by a TTL index on `createdAt`. Always create one through `notificationService.createNotification(userId, template(...), { session })` inside the caller's transaction (wording lives in `notification.templates.js`); order, registration and password-change already do. Endpoints: `GET /api/notifications`, `GET /api/notifications/unread-count` (the one the frontend polls), `PATCH /api/notifications/read-all`, `PATCH /api/notifications/:id/read`. Delete account removes them. `database/connection.js` runs `model.init()` for every model before the server accepts requests; without it, the first transaction to write into a brand-new collection can fail with a 500.
- Express 5 makes `req.query` a read-only getter, so `validate()` redefines it as an own property on the request (`Object.defineProperty`). Because of that, controllers receive validated query values: Joi defaults applied (`page=1`, `limit=20`) and numbers converted. Do not go back to `Object.assign(req.query, ...)`.
- **Market data** (`modules/market`): live quotes and indices (NIFTY 50, SENSEX) come from the FYERS API. `getMarketIndices` goes through a shared in-memory cache (`market.cache.js`): a quote under 30 s old is served without calling FYERS; simultaneous requests share ONE FYERS call (no stampede); after a failure FYERS is left alone for 5 s; if FYERS fails an earlier quote is returned labelled `stale: true` with its real `asOf` time for at most 5 minutes, after which the error is reported instead, so old data is never presented as live. Each index in the response has `stale` and `asOf`. The FYERS OAuth tokens are stored in a single-document `FyersToken` collection; the access token expires daily at 6:30 AM IST, after which `connectionStatus` becomes `reauthorization_required` and an admin must re-authorize via `GET /api/market/fyers/login`. Only the symbols in `market.constants.js` are supported. `scripts/test-fyers-refresh.js` is a manual script for testing token refresh.
- **Money** (`utils/money.js`): amounts stay plain Numbers in MongoDB (no migration) but ALL arithmetic is done on whole paise (`lineTotal`, `addMoney`, `subtractMoney`, `sumMoney`, `canAfford`, `roundMoney`) and rounded to 2 decimals before saving; per-share rates (average buy price) keep 6 decimals (`roundRate`); prices snap to the 5-paise tick (`roundToTick`). Never use `price * quantity` or `balance -= x` directly. Portfolio totals add the already-rounded rows.
- **Market hours** (`market/market.hours.js`, `market.holidays.js`, `market.status.js`): the market is open weekdays 9:15 AM to 3:30 PM IST except the holidays in `market.holidays.js` (one list per year, taken from NSE's calendar: add the new year every January; a year with no list logs a warning and counts weekdays as open). `getMarketStatus(now, { alwaysOpen })` is pure (IST is a fixed UTC+5:30, so it never depends on the server's timezone) and returns `{ isOpen, reason, tradingDay, holidayName, nextOpenAt }`; `getCurrentMarketStatus()` / `assertMarketOpen()` in `market.status.js` apply the `MARKET_ALWAYS_OPEN` override from config. `GET /api/market/status` adds `priceSource` and `serverTime`.
- **Simulated prices** (`modules/prices`): `server.js` (not `app.js`, so tests never start it) calls `startPriceJob()`, which runs `runPriceUpdate()` every 15 s (`price.job.js`, with an overlap guard; errors are logged, never thrown). `price.service.js` does nothing while the market is closed; otherwise it asks the provider for new prices and writes each stock with a condition INSIDE the write (`lastPriceUpdateAt` older than the current 15 s slot, or more than a minute in the future), so two racing runs or servers move a price only once. `price.provider.js` is the single place to swap in a real data vendor (same shape: `{ name, getNextPrices(stocks) }`); `simulated.provider.js` is a pure random walk: 25% yearly volatility scaled to 15 s steps (about 0.0407% per step, 1.58% a day), 5-paise ticks, kept within 10% of the previous close. Each Stock has `previousClose` (kept for the whole trading day, rolled to the last price on the first update of a new IST trading day), `tradingDay` and `lastPriceUpdateAt`, all stored in MongoDB so a restart loses nothing. Stock responses add `dayChange` and `dayChangePercent` (0 until a previous close exists). Cost is one write per stock per tick (about 15 ms each on Atlas): fine for tens of stocks, batch the writes if the list grows to hundreds.
- **Candles** (`modules/candles`): `recordCandles()` folds every moved price into a 5-minute and a daily OHLC candle with one atomic upsert each (`$setOnInsert` open, `$max` high, `$min` low, `$set` close), so restarts continue the same candle and nothing is lost to races. 5-minute candles expire 14 CALENDAR days after they start (TTL index on `expireAt`); daily candles are kept forever. `GET /api/stocks/:id/candles?range=1D|1W|1M|3M|1Y|ALL` returns `{ range, interval, candles: [{ time, open, high, low, close, synthetic }] }` oldest first (1D = the latest trading day that has candles). `scripts/backfill-market-history.js` gave the dev database a year of synthetic history (`synthetic: true`) generated backwards from the current price so it joins the live prices. The chart that uses this data comes in Phase 6.

## Frontend architecture (`client/src`)

- `app/router.jsx` defines routes: everything except `/login`, `/signup` and `/` is nested under `ProtectedRoute` → `AppLayout` (the app frame, below). **Every page is loaded on demand** with the `page(() => import("../pages/X.jsx"))` helper (React Router route-level `lazy`), so add new routes the same way; while a page downloads the current page stays on screen and `AppLayout` shows a thin progress bar. Errors are caught by `components/layout/RouteError.jsx` (a root `errorElement` for the whole app and a second one around the pages inside the frame, so a crashing or failed-to-download page replaces only the page and the navigation keeps working).
- Feature-sliced: `features/<name>/` holds a `<name>.api.js` (calls to the backend), `components/`, and optionally `hooks/` and `utils/`. `pages/` compose feature components; `components/ui/` holds shared primitives (Button, Card, Modal, ...); design tokens are in `styles/tokens.css`. Each component has a co-located `.css` file (plain CSS, no CSS framework).
- All HTTP goes through `lib/api.js` (a fetch wrapper with `credentials: "include"`). It attaches the access token from `AuthContext` (via `configureAuth`, see Automatic token renewal), unwraps JSON, and throws an `Error` with `.status` and `.data` (the backend error body) for non-2xx responses.
- `features/auth/AuthContext.jsx` keeps the access token only in memory (in state AND a ref that is set instantly, because the API client reads the ref); on app load it renews through `refreshSession()` (using the cookie) to restore the session.
- **Automatic token renewal** (`lib/api.js`): when a request fails with 401 `ACCESS_TOKEN_EXPIRED` / `ACCESS_TOKEN_INVALID`, the client calls `refreshSession()` and repeats the request ONCE. All requests that fail meanwhile share ONE renewal (a refresh token works only once; reusing it looks like theft), and `navigator.locks` (Web Locks) makes browser tabs take turns. If the renewal answers 401 the login is over (`onSessionExpired` -> AuthContext ends the session, reason `expired`); a 429, 5xx or network failure keeps the user logged in and the original request just fails. A wrong password (401 `INVALID_CREDENTIALS`) never triggers a renewal. `configureAuth({ getAccessToken, onTokenRefreshed, onSessionExpired })` wires AuthContext in; do not call `/api/auth/refresh` yourself, use `refreshSession()`. Logout waits for a renewal in progress (`waitForPendingRefresh`).
- **Idle timeout** (`features/auth/useIdleTimeout.js`, `idleActivity.js`): 30 minutes without user activity signs the user out (reason `idle`; the refresh token is revoked and the login page explains why via `location.state.sessionEndReason`). Activity = pointer, mouse move, key, wheel, scroll, touch and back/forward; polling and other background requests do NOT count. The last activity time is kept in `localStorage` (`tradeos-last-activity`) so other tabs count, a sleeping laptop is caught on wake, and reopening the app after 30+ minutes ends the login instead of restoring it. Change `IDLE_LIMIT_MS` in `idleActivity.js` to adjust (use 1 minute to test by hand).
- Forms use react-hook-form with zod schemas (`*.validation.schema.js`); icons come from `lucide-react`.
- Shared helpers live in `client/src/utils/` (`currency.utils.js`: `formatCurrency`, `formatCompactCurrency`; `date.utils.js`: `formatDateTime`); feature-specific helpers stay in `features/<name>/utils/`. All currency display goes through `formatCurrency` (do not write a local `Intl.NumberFormat`). Profit/loss and price-move helpers (`getPnlTone`, `formatSignedCurrency`, `formatSignedPercent`) are in `utils/change.utils.js`.
- **Theme** (`styles/tokens.css`): the dark "Indigo Desk" theme, the single source for colours, fonts, sizes, spacing, radius and shadows (`docs/plans/ui-redesign.md`). Surfaces rise from `--color-background` through `--color-surface`, `--color-surface-subtle` to `--color-surface-raised` (dropdowns, dialogs); text levels are `--color-text-primary/body/secondary/muted`; borders `--color-border`, `-subtle`, `-strong`, `-focus`. Marigold `--color-primary` is the brand and action colour (text on it: `--color-on-primary`). Green `--color-success` and red `--color-danger` mean ONLY up/profit/buy and down/loss/sell (text on solid fills: `--color-on-solid`); each status colour has a `-tint` background and a `-border`. Fonts: `--font-display` (headings, big numbers), `--font-sans`, `--font-mono` (prices and tables), self-hosted through `@fontsource-variable` in `main.jsx`. Use the type scale (`--font-size-2xs` ... `-4xl`), spacing (`--space-1..16`) and radius tokens. **Never write a hex colour in CSS**; use a token (or `color-mix()` on one). The page is dark only for now; a light theme would redefine the tokens.
- **Shared components** (`components/ui/`, see them all on the development-only page **`/dev/ui`**, which Vite removes from production builds; add every new shared component or state there): `Button` (variants primary / secondary / ghost / success = buy / danger = sell or delete, sizes sm / md / lg, `block`, `loading`), `Input` (label, error, `hint`, `id`, ref and other props passed through, eye icon for passwords), `Select` (`onChange` receives the value), `SegmentedControl` (Buy | Sell, time ranges; arrow keys; `tone`), `Card` (`as`, padding none / sm / md / lg), `Badge`, `Modal` (focus moves in, Tab is trapped, Esc closes, focus returns; `size`; pass `closeOnEscape` / `closeOnOverlayClick` = false while a request runs), `ResultState` (animated success tick or error cross, used for the order result), `Pagination` (page-number dots via `pagination.utils.js`, takes the backend `pagination` object plus an `itemLabel`; client-side lists build the same object, see `StocksPage`), `Table` (frame only: you write `<thead>` / rows; cell classes `data-table__num` and `data-table__actions`), `PriceChange` (the one way to show P&L or a price move), `EmptyState`, `LoadingSpinner` (small inline waits), `Avatar`. **Loading states of main pages use `Skeleton`** (`SkeletonRegion`, `SkeletonHeading`, `SkeletonTable` with `cardsBelow`, `SkeletonStats`, `SkeletonList`) laid out like the real page, never a bare "Loading..." line. Do not write one-off buttons, inputs, dropdowns, tables or dialogs: use these. CSS is global (not scoped), so give feature classes unique prefixes; two stylesheets used to clash on `.orders-table`.
- Lint gotcha: the `react-hooks/set-state-in-effect` rule rejects an effect that calls a function which sets state. Define the fetch function inside the `useEffect` (see `useOrders`, `usePortfolio`), and to refetch on demand bump a `refreshKey` state the effect depends on.
- **App frame** (`components/layout/`): `AppLayout` is a CSS grid (rail | top bar / page). `NavRail` is the 64px icon rail (desktop and tablet; name tooltips on hover and focus, marigold bar on the current page, Account at the bottom). On phones (max 768px, the ONE phone breakpoint) the rail is hidden and `BottomNav` appears (Dashboard, Stocks, Portfolio, Orders and a "More" sheet with Watchlist, Transactions and Account; respects the home-indicator safe area, which needs `viewport-fit=cover` in `index.html`). Both read the one list in `navigation.js`. `Navbar` is the top bar (logo on phones, `MarketStrip`, search, notifications, profile); `--navbar-height` (60px), `--rail-width` and `--bottom-nav-height` in `tokens.css` are the only place those sizes live, and dropdowns position from `--navbar-height`. `AppLayout` owns the single `<main id="main-content">` (plus a skip link): **pages must not render their own `<main>`**. `MarketStrip` (`features/market/useMarketIndices.js`) polls `GET /api/market/indices` every 60 s while the tab is visible; it shows nothing when there is no data, dims and labels "Delayed" quotes the server marks `stale`, and drops old numbers when a request fails. `ScrollRestoration` opens new pages at the top (known limit: Back also opens at the top, because pages load their data after they appear).
- Responsive pattern: wide-screen tables become cards on narrow screens. Both are rendered and CSS shows one (Orders and Stocks at about 768px, Transactions at 1000px, Portfolio holdings at 1100px because nine columns need the room).
- **Portfolio** (`pages/PortfolioPage.jsx`, `features/portfolio/`): `usePortfolio` loads `GET /api/portfolio` once (`refresh()` reloads quietly). The page shows summary cards, a hand-built SVG allocation donut (no chart library), a "Portfolio Value (7D)" placeholder, and `HoldingsSection` (search, sort, table or cards). Allocation, filter and sort logic is in `portfolio.utils.js`. Buy/Sell on a holding link to `/stocks/:id`; `?action=sell` opens `StockDetailsPage` on the Sell form.
- **Transactions** (`pages/TransactionsPage.jsx`, `features/transactions/`): read-only ledger from `GET /api/transactions` (10 per page), laid out like Orders. BUY amounts show as `-₹…`, SELL as `+₹…`. `useTransactions` keeps the requested page separate from the server's `pagination`, so a failed page change keeps the old rows and shows a banner. No filters or totals yet (they need backend support); see `docs/plans/transactions-page.md`.
- **Account** (`pages/AccountPage.jsx`, `features/account/`, route `/account`): five collapsible sections (Personal Information, Security, Trading Account, Preferences, Danger Zone) built on the shared `AccountSection` (all start closed, several can be open, closed panels are `inert`). Being built one section at a time; the plan and checklist are in `docs/plans/account-page.md`. Sections not built yet show `SectionPlaceholder`. `CurrentUserProvider` (mounted in `router.jsx` around `AppLayout`, so only for logged-in users) loads `GET /api/users/me` once and shares `{ user, setUser, loading, error, retry }` through `useCurrentUser()`; the Account page and the navbar `ProfileMenu` both use it, so an edited name or photo shows everywhere at once. Personal Information (`personal/PersonalInformation.jsx`) switches between `ProfileOverview` (with `AvatarUploader` for the photo) and `ProfileEditForm` (name only; email is read-only for now). A chosen photo opens `AvatarCropDialog` (hand-built square crop on a canvas, maths in `utils/avatarCrop.utils.js`, no library) and only the cropped JPEG is uploaded; the original may be up to 10 MB, the cropped file must be under the server's 2 MB. Clicking a saved photo opens `AvatarPreviewDialog` (full-size quick view with a "Change photo" shortcut). Security (`security/SecurityPanel.jsx`) holds change password (`ChangePasswordForm`), a disabled "Forgot password, coming soon" row and Log out. Trading Account (`trading/TradingAccountDetails.jsx`) is read-only: "Paper Trading", the balance from `GET /api/wallet` (fetched when the section is first opened) and an "Active" badge for everyone. Danger Zone (`danger/DeleteAccountPanel.jsx` + `DeleteAccountDialog.jsx`) deletes the account after a password re-check; on success it must `await navigate("/login", { flushSync: true, state })` BEFORE calling `logout()`, otherwise `ProtectedRoute`'s own redirect overrides it and the "account deleted" message is lost. Shared `components/ui/Avatar.jsx` shows the photo, else the initial. `lib/api.js` sends `FormData` bodies untouched (needed for the photo upload).
- **Notifications** (`features/notifications/`, `NotificationsProvider` mounted in `router.jsx` inside `CurrentUserProvider`; `useNotifications()` gives `{ unreadCount, items, pagination, markRead, markAllRead, refresh, ... }`): the provider **polls** `GET /api/notifications/unread-count` every 60 s (skipped while the tab is hidden, repeated at once when the tab returns) for the green count badge on the navbar bell (`components/layout/navbar/Notifications.jsx`, shows `99+` above 99). The list loads when the dropdown is first opened and is then kept fresh by the same polling tick. Mark one / mark all read are optimistic (screen first, undone with a banner if the request fails). Call `refresh()` after anything that creates a notification (already done after placing an order and changing the password). `formatRelativeTime` in `utils/date.utils.js` makes the "5 min ago" text. Polling goes through the same API client, so it gets renewed tokens like every other request, and it does not count as user activity for the idle timeout.
- **Navbar search** (`components/layout/navbar/StockSearch.jsx`, `useStockSearch.js`): loads `GET /api/stocks` each time the dropdown opens and filters in the browser with `matchesStockSearch` (shared with the Stocks page). Clicking a result, or highlighting one with the arrow keys and pressing Enter, opens `/stocks/:id`. Enter with nothing highlighted (or the "See all results" footer link) opens `/stocks?search=<text>`; `StocksPage` keeps its search text in that URL parameter. `/` or Ctrl/Cmd+K focuses the box.
- **Watchlist toggling** on the Stocks page goes through `features/watchlist/hooks/useWatchlistToggle.js` (loads the watchlist once; a 409 on add or 404 on remove just syncs the UI).
- **Market status and price refresh** (`features/market/`, `hooks/useVisiblePolling.js`): `MarketStatusProvider` (mounted in `router.jsx` inside `NotificationsProvider`) fetches `GET /api/market/status` once and every 60 s; `useMarketStatus()` gives `{ status, refresh }` (`status` is null until loaded: treat as unknown, the server decides on every order anyway). `MarketStatusBadge` shows "Market open/closed" and "Simulated" (when `priceSource` is `simulated`) on the dashboard, stocks, stock details, portfolio and watchlist pages. `useVisiblePolling(task, intervalMs = PRICE_REFRESH_MS)` runs a task every 30 s while the tab is visible (and at once when it returns), never two at a time, without counting as user activity; pages use it for a QUIET refresh (no skeleton, and a failed refresh keeps the old numbers). Used on the stock list, stock details and its position panel, portfolio, watchlist, and the dashboard's account summary and watchlist preview. `PlaceOrderCard` is disabled with the reason and next opening time while the market is closed, labels the total an estimate, and shows the execution price the server returned.

## Tests

The test database also holds about 1,400 leftover test stocks, so running the price job against it (a server with `MARKET_ALWAYS_OPEN=true`) is slow and loads the database; keep the market closed when running the browser regression scripts. Tests that need a specific market time pass their own `now`, or mock `market.hours.js`'s `getMarketStatus` (see `tests/orders.market.test.js`): never fake the whole system clock, it breaks login tokens. `testTimeout` is 20 s because the database is remote.

`server/tests/*.test.js` are integration tests that hit a real MongoDB (the `MONGODB_URI` in `.env.test`) through supertest; `server/test/setup.js` connects and disconnects. `tests/helpers/tradeosTestUtils.js` provides `createAuthenticatedUser()` (registers and logs in a unique user) and `createTestStock(price)`. Test data is not cleaned up between runs. `users.avatar.live.test.js` does a real Cloudinary upload and is skipped unless the three `CLOUDINARY_*` values are in the test process's environment (`.env.test` does not have them), so it is skipped in normal runs; to run it, pass those values to a single run without printing them or editing any env file. Test file names are inconsistent (`*.integration.test.js` / `*.integrated.test.js`), so match by path when running one.

## Git and GitHub workflow

The remote is https://github.com/Adarsh812793/TradeOS.git and the default branch is `main`. Changes reach `main` only through a pull request that the user reviews and merges on GitHub.

- **One branch per piece of work.** Never work directly on `main`. For every separate task (a bug-fix batch, a feature, a larger implementation) create a new branch from an up-to-date `main`, named by purpose, e.g. `feature/fixing-small-bugs`, `feature/<name>`, `fix/<name>`, `docs/<name>`.
- **Commits: allowed on my own, but say what they will be.** Claude may commit on the working branch without asking. Before committing, tell the user which commits are planned (one logical change per commit, e.g. "bug fixes", "lint cleanup", "dependency updates", "docs") and keep the messages descriptive. Check the staged files for secrets first, and never commit `.env*` files.
- **The last commit of every feature branch is the docs update.** When a feature or implementation is finished, its final commit updates the documentation: this file (Current Status, Known issues, Next Up, any architecture notes) and the relevant `docs/plans/*.md` checklists. Code and docs are then reviewed and merged together in the same PR. A separate docs-only branch (`docs/<topic>`, a new one per topic) is only for documentation changes that belong to no feature, such as changes to these rules.
- **Never push to `main`.** Do not push anything directly to `main`, ever. Always push to the specific branch that was created for the work. The user merges it into `main` through a pull request on GitHub.
- **Pushing a branch needs the user's say-so.** Ask before every push, every time; approval for one push does not carry over to the next. Ask, wait for the answer, then push only that branch.
- **Never close or delete branches** (local or remote) unless the user says so. Finished branches stay, because the user may come back to them to do more work related to that same feature. When the user asks for a branch to be deleted after it was merged, delete exactly that branch.
- **When the work is done:** leave the branch as it is (do not delete it), `git switch main`, then `git pull origin main` to get the merged code. Start the next task on a new branch.
- **Never** merge into `main` locally, force-push, rewrite published history, `git reset --hard` or skip hooks without being asked. The user does the review and the merge on GitHub.
- Commit messages end with the attribution line given in the session's system reminder.
